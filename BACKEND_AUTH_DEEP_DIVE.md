# Backend Auth Deep Dive

This document focuses only on the authentication and password-reset module of WealthMap’s backend. It is written as a compact technical reference so you can review the auth flow quickly before an interview and then jump back into the source files when you want the exact details.

## 1. Architecture Overview

WealthMap’s backend auth system is a stateless JWT-based login and password-reset flow built on Spring Boot, Spring Security, JPA, and Brevo email delivery. A user registers or logs in through the auth controller, Spring Security validates credentials through a custom `UserDetailsService`, a signed JWT is generated by `JwtUtil`, and that token is later checked by `JwtAuthFilter` on every protected request. Password recovery is handled by a separate OTP workflow that stores a temporary token in the database and sends it by email.

Top-level auth-related modules and their responsibilities:
- `controller`: exposes `/api/auth/**` endpoints for register, login, forgot password, and reset password.
- `config`: defines the Spring Security filter chain, CORS policy, password encoder, and authentication provider.
- `security`: contains JWT parsing/generation and the bridge from your `User` entity to Spring Security’s `UserDetails`.
- `service`: holds password reset and email delivery logic.
- `dto`: defines request/response shapes used by the auth endpoints.
- `entity`: stores the user account and password reset token data.
- `repository`: gives database access for user and reset-token lookup.

Typical auth request lifecycle:
1. User submits login/register form in the frontend.
2. The frontend sends JSON to `/api/auth/...`.
3. Spring MVC maps the JSON into a request DTO.
4. Controller validates the DTO and delegates to the service or security manager.
5. Spring Security checks credentials against `UserDetailsServiceImpl`.
6. `JwtUtil` generates or validates a signed JWT.
7. The token is returned to the frontend and stored there.
8. Future requests include the token in the `Authorization` header.
9. `JwtAuthFilter` validates the token and populates the `SecurityContext`.
10. Protected controllers can read `authentication.getName()` and use it for ownership checks.

Major technologies used here and why they matter in this project:
- Spring Boot: boots the backend and wires the auth beans automatically.
- Spring Security: handles login authentication, request authorization, and the filter chain.
- JWT: keeps the app stateless so the server does not need session storage.
- BCrypt: stores passwords securely instead of plain text.
- JPA/Hibernate: persists users and password-reset tokens.
- Brevo HTTP API: sends OTP and invite emails from the backend.
- Java HttpClient: performs outbound email API calls without adding more dependencies.

Auth-related features in this module:

### Feature: Registration

**What it does**
Creates a new user account, hashes the password, saves the record, and returns a JWT plus basic user profile data so the frontend can log the user in immediately.

**Files involved**
- `wealthmap-backend/src/main/java/com/wealthmap/controller/AuthController.java`
- `wealthmap-backend/src/main/java/com/wealthmap/dto/request/RegisterRequest.java`
- `wealthmap-backend/src/main/java/com/wealthmap/entity/User.java`
- `wealthmap-backend/src/main/java/com/wealthmap/repository/UserRepository.java`
- `wealthmap-backend/src/main/java/com/wealthmap/security/UserDetailsServiceImpl.java`
- `wealthmap-backend/src/main/java/com/wealthmap/security/JwtUtil.java`
- `wealthmap-backend/src/main/java/com/wealthmap/dto/response/AuthResponse.java`

**Step-by-step trace**
1. `AuthController.register(...)` receives the JSON body as `RegisterRequest`.
2. `@Valid` triggers bean validation before the method body runs.
3. `userRepository.existsByEmail(...)` prevents duplicate accounts.
4. A `User` entity is created and populated.
5. `passwordEncoder.encode(...)` hashes the raw password with BCrypt.
6. `userRepository.save(user)` persists the account.
7. `userDetailsService.loadUserByUsername(...)` loads the freshly created user as Spring Security `UserDetails`.
8. `jwtUtil.generateToken(...)` creates a signed JWT.
9. `new AuthResponse(...)` is returned to the client.

**State management**
- Local request state: the submitted registration payload.
- Database state: persistent user account and hashed password.
- Client state: JWT and user profile stored in frontend auth storage.

**Validation & error handling**
- Blank name/email/password and malformed email are blocked by DTO validation.
- Duplicate email returns `400 Bad Request`.
- There is no separate password-strength policy beyond minimum length.

**Edge cases**
- Duplicate registration is handled.
- Missing or invalid request fields are handled.
- If user persistence succeeds but JWT generation fails, the controller does not explicitly compensate, so this is a small transactional/consistency risk.

### Feature: Login

**What it does**
Authenticates a user with email and password, then returns a signed JWT and user details for the frontend session state.

**Files involved**
- `wealthmap-backend/src/main/java/com/wealthmap/controller/AuthController.java`
- `wealthmap-backend/src/main/java/com/wealthmap/dto/request/LoginRequest.java`
- `wealthmap-backend/src/main/java/com/wealthmap/config/SecurityConfig.java`
- `wealthmap-backend/src/main/java/com/wealthmap/security/UserDetailsServiceImpl.java`
- `wealthmap-backend/src/main/java/com/wealthmap/security/JwtUtil.java`
- `wealthmap-backend/src/main/java/com/wealthmap/dto/response/AuthResponse.java`

**Step-by-step trace**
1. `AuthController.login(...)` receives the request body.
2. `AuthenticationManager.authenticate(...)` checks email/password against the configured `AuthenticationProvider`.
3. `DaoAuthenticationProvider` calls `UserDetailsServiceImpl.loadUserByUsername(...)`.
4. Spring Security compares the provided password with the stored BCrypt hash.
5. If authentication passes, the controller fetches the `User` entity from `UserRepository`.
6. `JwtUtil.generateToken(...)` creates the JWT.
7. `AuthResponse` returns token plus user details.

**State management**
- No server session is created.
- JWT becomes the only persisted login state on the frontend.
- Backend request authentication is reconstructed from the token on each request.

**Validation & error handling**
- DTO validation blocks malformed email or blank password before authentication.
- Wrong password or unknown user fails inside Spring Security.
- The controller itself does not catch login exceptions, so Spring’s default auth error handling applies.

**Edge cases**
- Expired account/session state is not stored server-side because auth is stateless.
- Repeated login attempts are not rate-limited in the code shown, so brute-force protection is not explicit here.

### Feature: JWT request authentication

**What it does**
Validates the Bearer token on every protected request and reconstructs the authenticated user inside Spring Security’s context.

**Files involved**
- `wealthmap-backend/src/main/java/com/wealthmap/config/SecurityConfig.java`
- `wealthmap-backend/src/main/java/com/wealthmap/security/JwtAuthFilter.java`
- `wealthmap-backend/src/main/java/com/wealthmap/security/JwtUtil.java`
- `wealthmap-backend/src/main/java/com/wealthmap/security/UserDetailsServiceImpl.java`

**Step-by-step trace**
1. The frontend sends a request with `Authorization: Bearer <token>`.
2. `JwtAuthFilter.doFilterInternal(...)` intercepts the request.
3. If the header is missing or not Bearer format, the filter does nothing and passes the request forward.
4. `jwtUtil.extractUsername(...)` reads the token subject.
5. `userDetailsService.loadUserByUsername(...)` loads the Spring Security user.
6. `jwtUtil.validateToken(...)` checks subject match and expiration.
7. A `UsernamePasswordAuthenticationToken` is created and stored in `SecurityContextHolder`.
8. Controller methods can now use `Authentication authentication`.

**State management**
- Token is stored client-side in localStorage.
- Auth state is created per request on the server.
- No HTTP session is used.

**Validation & error handling**
- Missing Authorization header is allowed through so public endpoints still work.
- Invalid token parsing is caught and logged.
- Invalid token validation does not authenticate the request.

**Edge cases**
- Expired tokens are rejected.
- Requests without tokens simply remain unauthenticated.
- If token parsing fails, the filter logs the error and still passes the chain forward.

### Feature: Password reset request

**What it does**
Starts a password-reset flow by generating a one-time code, storing it temporarily, and emailing it to the user.

**Files involved**
- `wealthmap-backend/src/main/java/com/wealthmap/controller/AuthController.java`
- `wealthmap-backend/src/main/java/com/wealthmap/dto/request/ForgotPasswordRequest.java`
- `wealthmap-backend/src/main/java/com/wealthmap/service/PasswordResetService.java`
- `wealthmap-backend/src/main/java/com/wealthmap/entity/PasswordResetToken.java`
- `wealthmap-backend/src/main/java/com/wealthmap/service/EmailService.java`
- `wealthmap-backend/src/main/java/com/wealthmap/repository/PasswordResetTokenRepository.java`
- `wealthmap-backend/src/main/java/com/wealthmap/repository/UserRepository.java`

**Step-by-step trace**
1. `AuthController.forgotPassword(...)` receives the email address.
2. `PasswordResetService.generateAndSendOtp(...)` looks up the user.
3. Existing reset tokens for that user are deleted.
4. A 6-digit OTP is generated.
5. A `PasswordResetToken` entity is created with a 15-minute expiry.
6. The token is saved.
7. `EmailService.sendOtpEmail(...)` sends the code by Brevo.

**State management**
- OTP exists in the database only until it is used or expires.
- Frontend does not know the OTP; it only knows that an email was sent.

**Validation & error handling**
- Unknown email returns a runtime error.
- The controller catches runtime errors and returns `400 Bad Request`.
- Email send failures bubble up as runtime exceptions.

**Edge cases**
- Existing tokens are invalidated when a new OTP is requested.
- OTP generation uses `Random`, which works but is not ideal for security-sensitive generation.
- If email sending fails after DB save, the token may still exist, so the user might get a valid code even though the API reported failure.

### Feature: Password reset confirmation

**What it does**
Checks the OTP, verifies expiry, updates the password, and clears the reset token.

**Files involved**
- `wealthmap-backend/src/main/java/com/wealthmap/controller/AuthController.java`
- `wealthmap-backend/src/main/java/com/wealthmap/dto/request/ResetPasswordRequest.java`
- `wealthmap-backend/src/main/java/com/wealthmap/service/PasswordResetService.java`
- `wealthmap-backend/src/main/java/com/wealthmap/entity/PasswordResetToken.java`
- `wealthmap-backend/src/main/java/com/wealthmap/entity/User.java`

**Step-by-step trace**
1. `AuthController.resetPassword(...)` receives email, OTP, and new password.
2. `PasswordResetService.verifyAndResetPassword(...)` loads the user.
3. The active reset token is fetched from the database.
4. The submitted OTP is compared with the stored OTP.
5. Expiry is checked against `LocalDateTime.now()`.
6. If valid, the password is re-hashed with BCrypt.
7. The user record is saved.
8. The reset token is deleted.

**State management**
- Database owns the reset token lifecycle.
- Frontend only controls the form input.

**Validation & error handling**
- Invalid OTP returns an error.
- Expired OTP is deleted and rejected.
- Missing active reset request is rejected.

**Edge cases**
- Multiple reset attempts are prevented because only one active token is kept per user.
- The use of `@Transactional` helps keep password update and token cleanup consistent.

### Feature: User lookup and password hashing

**What it does**
Bridges the app’s `User` entity to Spring Security and stores passwords using a secure hashing algorithm.

**Files involved**
- `wealthmap-backend/src/main/java/com/wealthmap/security/UserDetailsServiceImpl.java`
- `wealthmap-backend/src/main/java/com/wealthmap/repository/UserRepository.java`
- `wealthmap-backend/src/main/java/com/wealthmap/entity/User.java`
- `wealthmap-backend/src/main/java/com/wealthmap/config/SecurityConfig.java`

**Step-by-step trace**
1. Spring Security asks `UserDetailsServiceImpl` for a user.
2. `UserRepository.findByEmail(...)` loads the account.
3. A Spring Security `User` object is created with email, hashed password, and no authorities.
4. `BCryptPasswordEncoder` is used whenever passwords are written or verified.

**State management**
- The persistent truth is the DB-stored password hash.
- The Spring Security `UserDetails` object is temporary request/authentication state.

**Validation & error handling**
- Unknown email becomes `UsernameNotFoundException`.
- Password comparison happens inside Spring Security, not in controller code.

**Edge cases**
- There is no role-based authorization yet because authorities are empty.
- That means the app is using authentication only, not fine-grained roles.

## 3. Library & Pattern Justification

- **Spring Security**
  - Solves login, token validation, endpoint protection, and credential checking.
  - Without it, the app would need custom auth and password verification code everywhere.
  - Alternative: session-based auth. Tradeoff: simpler in some apps, but not as clean for SPA/API separation.
  - This looks like a deliberate choice, not an AI default.

- **JWT**
  - Solves stateless authentication for the frontend and API split.
  - Without it, the server would need sessions or some other state store.
  - Alternative: OAuth2 or server sessions. Tradeoff: more infrastructure or more dependency on server memory/state.
  - Deliberate and appropriate here.

- **BCrypt**
  - Solves secure password storage.
  - Without it, passwords would be plain text or weakly hashed.
  - Alternative: Argon2. Tradeoff: also strong, but BCrypt is perfectly acceptable and widely supported.
  - Deliberate and standard.

- **`UserDetailsService` bridge**
  - Solves integration between your `User` entity and Spring Security’s auth engine.
  - Without it, Spring would not know how to look up users from your database.
  - Alternative: custom auth provider with manual queries. Tradeoff: more code, more control.
  - Deliberate and standard.

- **`OncePerRequestFilter`**
  - Solves token validation exactly once per request.
  - Without it, you would have to manually validate the JWT inside each controller or custom interceptor.
  - Alternative: MVC interceptor. Tradeoff: good for some cases, but security filters are the idiomatic Spring Security approach.
  - Deliberate and correct.

- **CORS config with wildcard origin**
  - Solves frontend-backend cross-origin access during deployment.
  - Without it, browser calls from the frontend origin may fail.
  - Alternative: whitelist only production frontend domains. Tradeoff: safer and preferred for production.
  - This may be a pragmatic deployment choice, but it should be re-evaluated for production.

- **Database-stored OTP reset tokens**
  - Solves password-reset state without relying on in-memory server storage.
  - Without it, OTP validation across requests would be fragile.
  - Alternative: Redis-backed OTPs. Tradeoff: better expiry control and faster invalidation, but extra infrastructure.
  - Deliberate, though a Redis approach would be more production-grade.

- **Email API through Brevo**
  - Solves transactional email delivery for OTPs and invitations.
  - Without it, the app could not send password-reset or family-invite emails.
  - Alternative: SMTP server or another email provider. Tradeoff: similar capability, different cost/ops profile.
  - Deliberate integration choice.

## 4. Database & Data Model

Auth-related tables currently used in this module:
- `users`
  - Stores `id`, `email`, `password`, `name`, `mobile_number`, `createdAt`, and optional `family_group_id`.
  - `email` is unique and not null.
- `password_reset_tokens`
  - Stores `id`, `otp`, `user_id`, and `expiryDate`.
  - One token is associated with one user.

Relationships:
- `User` belongs to an optional `FamilyGroup`.
- `PasswordResetToken` has a one-to-one relationship with `User`.

Access rules in plain English:
- Registration checks that email is unique in application code.
- Login depends on Spring Security and password hashing, not DB policies.
- Password reset is restricted by the matching OTP and token expiry.

Where integrity depends on application code rather than the DB:
- Duplicate account prevention is handled in the controller, not by a DB constraint alone.
- OTP expiry enforcement is checked in service code.
- Token invalidation on new reset requests is handled in service code.

Risk note:
- If application code is bypassed or changed incorrectly, the DB will not fully enforce the auth rules by itself.

## 5. Security & Auth Flow

Full auth flow:
1. User opens login or register page in the frontend.
2. Frontend sends credentials to `/api/auth/register` or `/api/auth/login`.
3. `AuthController` handles the request.
4. `SecurityConfig` allows auth endpoints without authentication.
5. On login, `AuthenticationManager` checks the credentials using `DaoAuthenticationProvider`.
6. `UserDetailsServiceImpl` loads the user record from the database.
7. `BCryptPasswordEncoder` verifies the password hash.
8. `JwtUtil` creates a signed JWT.
9. Frontend stores token and user info.
10. For later requests, Axios attaches the token in the `Authorization` header.
11. `JwtAuthFilter` validates the token and populates Spring Security’s context.
12. Protected controllers can now trust `authentication.getName()`.

Authorization checks happen at these layers:
- Client: the frontend hides protected routes when auth state is missing.
- Server: `SecurityConfig` blocks non-authenticated requests for everything except `/api/auth/**`.
- Service/controller: ownership checks compare the authenticated user to the loaded entity owner.

Gaps to be ready for:
- No role-based authorization is implemented yet.
- CORS is permissive and should be tightened for production.
- Login rate limiting is not visible in the code.
- OTP generation should ideally use `SecureRandom`.
- The auth controller mixes constructor injection with field injection.

## 6. Likely Interview Questions

### Registration and login
- **Why do you call `UserDetailsService.loadUserByUsername(...)` right after saving a user?**
  - Because Spring Security’s JWT generator works with `UserDetails`, and the app treats email as the username.

- **Why does login go through `AuthenticationManager` instead of comparing passwords yourself?**
  - Because Spring Security already knows how to verify the hash through the configured provider, which keeps auth logic centralized.

- **Why return JWT plus user details in `AuthResponse`?**
  - So the frontend can store both the session token and current profile state in one response.

### JWT security
- **Why use a `OncePerRequestFilter` for JWT validation?**
  - Because every API call must be checked once, before reaching protected controllers.

- **What happens if the Authorization header is missing?**
  - The filter just passes the request through, and protected endpoints will still fail later due to missing authentication.

- **Why keep the app stateless?**
  - Because JWT already carries the auth state, so server sessions are unnecessary.

### Password reset
- **Why store the OTP in the database instead of memory?**
  - Because the reset flow spans multiple requests and needs durable state until the token is used or expires.

- **Why delete old OTP tokens when a new one is generated?**
  - To prevent multiple active reset codes from being valid at once.

- **Why does expiry live in the entity?**
  - So the token object itself carries its own lifetime and the service can validate it consistently.

## 7. Things I Should Be Able to Defend

- **Stateless JWT auth instead of server sessions**
  - Strong justification: it fits a frontend-backend split very well and avoids server-side session storage.

- **BCrypt for password storage**
  - Strong justification: it is standard, safe, and supported directly by Spring Security.

- **Wildcard CORS with credentials**
  - Weak justification: it helps deployment, but it is risky and should probably be narrowed before production.

- **Password reset OTP stored in the database**
  - Strong justification: it makes the reset flow durable across requests and restart-safe.

- **`Random` for OTP generation**
  - Weak justification: it works, but it is not ideal for security-sensitive token generation and should probably be replaced with `SecureRandom`.

- **Mixing constructor injection and field injection in `AuthController`**
  - Weak justification: it works, but it is inconsistent and should be cleaned up for maintainability.

## 8. Mechanism-Level Line-by-Line Trace

### Mechanism: Authentication and session management

**Entry point**
- Login starts in `wealthmap-backend/src/main/java/com/wealthmap/controller/AuthController.java` in `login(...)`.
- Subsequent authenticated requests enter through `wealthmap-backend/src/main/java/com/wealthmap/security/JwtAuthFilter.java`.

**Full call chain**
1. `AuthController.login(...)`
2. `AuthenticationManager.authenticate(...)`
3. `DaoAuthenticationProvider`
4. `UserDetailsServiceImpl.loadUserByUsername(...)`
5. `UserRepository.findByEmail(...)`
6. `JwtUtil.generateToken(...)`
7. `JwtAuthFilter.doFilterInternal(...)`
8. `JwtUtil.extractUsername(...)`
9. `JwtUtil.validateToken(...)`
10. `SecurityContextHolder.setAuthentication(...)`

**Line-by-line walkthrough highlights**
- `authenticationManager.authenticate(new UsernamePasswordAuthenticationToken(...))`
  - Kicks off Spring Security’s credential verification.
  - If removed, the app would not actually verify the password on login.
- `userDetailsService.loadUserByUsername(email)`
  - Bridges the database user into Spring Security format.
  - If removed, Spring would not know how to resolve the principal.
- `jwtUtil.generateToken(userDetails)`
  - Builds a signed JWT with subject, issue time, and expiry.
  - If removed, the app would have no stateless session token.
- `request.getHeader("Authorization")`
  - Reads the bearer token from the request.
  - If missing, the request remains unauthenticated.
- `jwtUtil.extractUsername(jwt)`
  - Reads the token subject.
  - If the token is malformed, parsing fails and the filter logs the error.
- `jwtUtil.validateToken(jwt, userDetails)`
  - Checks identity match and expiry.
  - If this is removed, forged or expired tokens could be accepted.
- `SecurityContextHolder.getContext().setAuthentication(authToken)`
  - Makes the user available to controllers for the lifetime of this request.

**State/data at each step**
- Before login: no token exists, request only contains email/password.
- After successful login: client receives `{ token, id, email, name, mobileNumber }`.
- Before protected request: frontend stores token in localStorage.
- After filter validation: Spring Security context contains authenticated principal.

**Failure paths**
- Invalid password: authentication fails inside Spring Security.
- Invalid/expired token: filter does not set authentication.
- Missing token: request remains anonymous.
- Malformed token: exception is logged and the chain continues without auth.

**External dependencies**
- JWT signing uses the Base64 secret from configuration.
- Email delivery is external only for password-reset and invite workflows.

**Boundary/edge cases**
- Expired JWTs are rejected.
- Requests without tokens are allowed through but remain unauthenticated.
- No role claims are enforced because authorities are empty.

**Plain-English summary**
This auth system is stateless. The user logs in with email and password, Spring Security verifies the credentials, and the backend returns a signed JWT. The frontend stores that token and sends it back on later requests. A custom filter validates the token on every protected request and puts the user into Spring Security’s context so controllers can know who is calling them. Password resets are handled separately with OTP tokens stored in the database and emailed to the user.
